# Dave Mirra Freestyle BMX — port plan

Goal: a C17 + SDL3 reimplementation of `NgBMX.exe` (sha256 in `tools/known_exe.txt`) that plays identically to the
original, then gains ultrawide / high-fps / gamepad / renderer upgrades behind options. No original code or
assets in the repo; everything is loaded from the user's install.

Scope (`data/functions.csv`): 2,115 functions to port, 1,403 game and 712 engine (492 KB). RenderWare 3,
the CRT, zlib and libpng (~1,300) are replaced, not decompiled. The first estimate (2,537) included jump
tables, padding and switch-case fragments the seeding mistook for functions. That was fixed on 2026-10-19.

## Strategy: incremental hook-replacement, with the original as the test oracle

Don't do a big-bang rewrite and don't do a byte-matching decomp:

- **Byte-matching** (recompiling with MSVC6 until the bytes are identical) is the most reliable signal, but it
  costs many tokens per function and buys nothing for a port.
- **A big-bang rewrite** can't be tested until everything is done. That's where the bugs come from.

Instead, follow the re3 / OpenRCT2 approach:

1. **Hook phase.** Build `bmx.dll` (clang-cl, i686) and inject it into the original exe. It patches the
   incremental-link table: each of the 1,130 jump stubs at 0x401005 is one 4-byte write to redirect a
   function. The game stays playable after every single function swap, so a regression points at exactly
   one function.
2. **Platform flip.** Once game and engine logic are in C, replace RenderWare / D3D7 / DirectSound /
   DirectInput with our own layer on SDL3. The exe is no longer needed and builds go native 64-bit
   (macOS arm64, Linux, Windows x64, Android).
3. **Enhancements**, all behind options, only after parity is reached.

## Verification ladder (cheapest first)

| Level | What | Runs where |
|---|---|---|
| 1 | Builds with `-Wall -Wextra -Werror`, clang-tidy, clang-format check | everywhere, pre-commit + CI |
| 2 | **Differential unit tests.** Run each original function in Unicorn (x86 emulator) on the user's exe, run ours natively, compare return value plus touched memory. Inputs: fuzzed + **recorded real arguments** (the hook DLL logs args/state at function entry during play sessions → corpus) | macOS/Linux, no Wine needed |
| 3 | **Golden traces.** Scripted input playback (replay.c already records inputs). Compare per-frame rider/physics/score state between original and hook build | nixbox (x86_64 Linux + Wine + Xvfb) |
| 4 | **Screenshot diffs** at fixed frames (perceptual threshold), for the renderer flip | nixbox |
| 5 | Human playtest checklist per milestone (all levels, modes, menus, replays, save/load) | you |

Floating point (**verified on the zquat pilot, 9/9 functions bit-exact over 5,000 iterations each**):
Windows runs the x87 at 53-bit precision, so a value in an x87 register is exactly a C `double` and an
`FSTP float` is a rounding to `float`. Ports model that explicitly and build with SSE2 strict IEEE, which
gives bit-exact results against the original on every platform. Physics can therefore stay
deterministic-identical, and tests default to 0 ULP tolerance. Two caveats found on the way:
Ghidra's pseudo-C regroups FP sums (so translate FP from the disassembly), and LLVM's x87 backend doesn't
round floats (so the hook build uses SSE2, not x87). Rules are in CONTRIBUTING.md.

## Token / time efficiency

1. **Deterministic tooling does everything that isn't translation.** One Ghidra headless export writes one
   JSON bundle per function: pseudo-C, disasm, callers, callees, strings, assert file, and known types. Agents
   never open Ghidra or explore the repo. Stubs, hook tables, headers, the progress report and test scaffolds
   are all generated by scripts.
2. **The unit of work is a big slice:** whole source files grouped to ~60–120 functions, ordered bottom-up
   by the call graph (`tools/slice.py plan`). Per-slice overhead dominates on small slices (measured on
   the NFSMW port), so slices stay large. Each agent gets a single packet file
   (`tools/slice.py packet`) and doesn't explore the repo.
3. **Model ladder**, re-tuned from measured pass rates:
   - **No LLM:** functions ≤16 bytes (~420). Returns, getters and empty PSX stubs are templated by script.
   - **Haiku:** mechanical follow-ups such as renames, clang-tidy fixes, and classifying test failures.
   - **Sonnet (default):** translating functions, batched 5–15 small functions per call within one file,
     including their differential tests.
   - **Opus:** struct/type recovery, the ~80 functions over 1 KB, anything Sonnet fails twice,
     cross-module design, and code review of each finished module.
4. **Closed loop:** compile errors and diff-test failures go back to the same agent automatically (max 2
   retries, then escalate). No human or Opus in the inner loop.
5. **Prompt caching:** a stable shared prefix (style guide + `types.h` + conventions) and the per-function
   bundle last.
6. **Slice by difficulty, not only by file** (learned 2026-10-19):
   - Sonnet ported a 62-function utility slice bit-exact on its first test run, at ~4.4k tokens per
     function.
   - The same model spent 453k tokens on `physics.c` (76 rows, 45 KB, FP-heavy, packet ~148k tokens) and
     ported nothing.
   - Rules: cap packets at ~50k tokens. Give the large FP functions (≥1 KB with x87, 88 of them) to Opus
     in small groups after their callees are ported. Give Sonnet everything else in big slices.
7. **Pilot before scaling:** run `zquat.c`, `zstring.c`, `zlist.c` and part of `physics.c` end to end. Measure
   tokens per function, first-try pass rate and wall time, then extrapolate and tune the ladder. Rough prior:
   ~2,100 LLM-handled functions × ~10–15k tokens ≈ 20–30M tokens for the bulk pass.

## Code quality rules

- C17, CMake + presets + Ninja, all tools pinned in a Nix flake devshell.
- Only clang-format decides formatting. clang-tidy runs with a curated set (bugprone-*, cert-*, readability-*
  subset). The native build runs under ASan + UBSan in CI. cppcheck runs nightly.
- Every ported function carries an `// addr: 0x425940` annotation. The progress tool (functions/bytes ported
  per module) reads these annotations.
- Keep Z-Axis naming wherever the asserts reveal it (`zsndSeq…`, `kzsndSeqMaxTracks`). Ghidra stays the
  single source of truth for names and types, synced both ways by script.
- **64-bit hazard:** PSX-style assets are loaded straight into structs with pointer fixups (`zramdisk`,
  `ziff`, `zasset`). In-memory structs and on-disk structs are separate types from day one. On-disk ones use
  fixed-width offsets with explicit (de)serialisers. Layouts are pinned with `static_assert` in the i686 build.
- Keep enhancements out of the faithful code path: options plus separate modules, with the original
  behaviour as the default.

|---|---|---|---|

| P1 | Types & map (Opus) | core structs (actor, rider, zobj, asset, scene), globals, function→file assignment, community labels imported | ≥90% of A/B functions assigned to a file |

## Facts that drive the plan

- Host Mac is arm64. Level-2 tests run in Unicorn anywhere. Levels 3/4 (real game under Wine) need nixbox (x86_64).
- Videos are Cinepak 320×240 AVI (simple decoder). Assets are RenderWare stream v0x0301 plus Z-Axis
  ZMD/ZSD containers. bleeds187/dmfbmx documents the containers.
- Prior art to import: fromasmtodisasm/DAVE-MIRRA-LABELS (892 labels).

## Decisions

- Renderer: SDL3 GPU API.
- Hosting: Forgejo on nixbox (`denzo/opendmfbmx`), with a Linux docker runner. Pushes to main are fine,
  but batch them.
- Target exe: the one we have (sha256 `97aa9077…`), from the DEViANCE repack.
- No game video or audio is launched without explicit permission. Emulator tests are headless and silent.
- **Vanilla stays vanilla.** Every enhancement is opt-in and defaults off. With all options off, the build
  must match the original bit for bit (golden traces are the gate), on every platform: build with
  `-ffp-contract=off` so ARM FMA can't drift physics. Ported functions stay as decompiled; enhancements
  attach at seams (main loop, renderer, input, audio), not as option checks inside faithful code.
  Options are tagged visual-only or gameplay-changing; replays and saves record the gameplay-changing ones.
- **Exception (2026-10-31, the user's call):** the native exe's input conveniences `dpad_steering` and
  `stick_8way` (bmxnative.ini `[input]`) default **on**: the original reads only the stick (axial 10% dead
  zone), which makes pure directions (backflip) very hard on a thumbstick. They act on the pad's lX/lY only,
  after `BMX_INPUT_CHECK` compares, so the game still sees DirectInput-shaped input; `= 0` gives vanilla.
  Likewise `[audio] smooth_resample` defaults to 2 (cubic interpolation in a copy of the effects mixer
  instead of the original zero-order hold); `= 0` gives the original mixer.
- **Exception (2026-10-31, the user's call):** `[ui] confirm_quit` defaults to **0**: the main menu's QUIT no
  longer asks "Do you want to quit the game?" (the MessageBoxA stand-in answers Yes to exactly that box);
  `= 1` shows it as the original did. Every other message box (asserts, errors) still shows.
- **Option (2026-11-01, the user's call):** `[video] full_draw_distance = 1` (default 0, vanilla) keeps the far
  clip and fog at their maximum (200). The original's frame rate adapter (ngiffxAdaptQuality) reads the level load as
  ~2.5 fps, drops the far clip to 60 and needs ~20 s to climb back, so levels start with distant geometry missing.
  Visual only (BMX_SIM_HASH identical); on in the user's personal ini.
- **Defaults (2026-11-01, the user's call after a long playtest):** the native exe's enhancements are **on** by
  default: the desktop resolution (`width = height = 0`), `widescreen = 1`, `hud = 1`, `menus = 2`, `ui_filter = 2`,
  `interpolate = 1`, `full_draw_distance = 1` (with the earlier `smooth_resample = 2`, `dpad_steering`,
  `stick_8way`, `confirm_quit = 0`). One switch, `[general] vanilla = 1`, gives the original game for every option
  the ini does not set (bmxConfigOption, config.c). All of them are visual or input conveniences; none changes the
  simulation (BMX_SIM_HASH checked for each).
- **64-bit and other platforms (2026-11-01, the user's call; docs/PORTING.md):** one 64-bit codebase for Windows x64,
  Linux x64, macOS arm64 and Android arm64, with the 32-bit builds as the bit-exact reference. The original's
  initialised data (~70 KB of tables and strings) moves into the source as named C initialisers, like the code;
  builds then need only the game's data folders, not NgBMX.exe, and can be released. The game's files (levels,
  models, textures, sounds, movies, music) and NgBMX.exe are never in the repo or a release. arm64 gets bit-exact
  portable versions of the x87 operations, so the simulation is identical on every platform.

## Enhancement backlog (P6+, unordered)

- Ultrawide (hor+), high fps via fixed-timestep physics + render interpolation, gamepad, lighting.
- (Retro)Achievements, ideally with in-game popups.
- Content from other Dave Mirra titles (Maximum Remix, Dave Mirra 2): check PC availability and formats.
- Code differences from Maximum Remix, if a binary with the same engine is available to diff against.
- Uncompressed / higher-quality audio. Music: done 2026-10-31 as an opt-in override (`[audio] music_dir`): the
  game's edits rebuilt in stereo from the user's own FLACs, at the DirectSound stand-in (docs/MUSIC.md
  "Override"). Left: the effects and speech (22 kHz and lower in the game's banks; no better source).
- Remastered menu graphics.
- Compatibility (default on, behaviour-neutral): no DX7/DirectShow/CD dependencies (Cinepak decoder,
  SDL audio); saves and settings in the user profile, not the install dir or registry; any resolution,
  borderless/windowed, alt-tab, DPI awareness, vsync; SDL gamepad DB with correct prompts, hot-plug,
  rumble, key rebinding; crash fixes for original bugs found while porting (uninitialised stack in the
  device dialog, skid fps 0 divide, zrwEpicFail buffer overflow, NULL reads before checks) — anything
  that changes normal-play behaviour becomes an option instead.
- PS1 blend modes (opt-in, ~2-3 days): the PC port collapses the PS1 semi-transparency modes in ngifpsx.c
  blendFlags() to D3D7 states (mode 2 B-F becomes a multiply, mode 3 B+F/4 a full add, mode 0 a vertex-alpha
  fake); the SDL3 driver can render the real maths (reverse subtract, quarter add) if the ABR is carried down as
  a render state. Visible in overlay fades/bars and HUD text. (Checked 2026-10-31: looping sounds are culled and
  vertex colours are PC-authored 0..255, so those PS1-vs-PC issues of other ports do not apply here.)
- Graphics options: texture filtering, MSAA/anisotropic, shadow resolution, draw/fog distance, HUD
  anchoring for widescreen/ultrawide, UI scaling.
- RTX Remix: hooks only D3D9 fixed-function. Try now on the original exe via a DX7→D3D9 wrapper
  (dgVoodoo2/dxwrapper). For our build: optional D3D9 fixed-function backend on Windows (decide in P4).
- Vendor-neutral ray/path tracing (preferred long-term over Remix-only): separate Vulkan RT backend
  (NVIDIA/AMD RDNA2+/Intel), optionally Metal RT; SDL3 GPU has no RT. Precedent: Quake II RTX. The
  real work is PBR materials (override folder shared with Remix), lights (original is mostly baked
  vertex colour) and a vendor-neutral denoiser (SVGF or FidelityFX). P4 must put the renderer behind a
  backend interface so this and the Remix D3D9 path are add-ons.
- DLSS / FSR upscaling: needs depth + motion vectors (also needed for render interpolation). SDL3 GPU
  may not expose enough for the vendor SDKs; decide in P4 whether a D3D12/Vulkan backend is needed.
- Modding: asset override folder (menus, riders, bikes), custom music, later a Blender level exporter.
- Level remaster (render-only replacement pack, opt-in):
  - **Rule:** collision always stays on the original triangles. Grinds, lips and landings depend on
    the exact faces and edges, and the physics is bit-exact against them. Render meshes stay within
    ~1–2 cm of the original surfaces.
  - **Pipeline:** export each level to glTF (geometry, UVs, vertex colours, textures; gameplay
    metadata such as edges, spawns and props in glTF extras), then a reproducible Blender Python
    script rather than hand rebuilds or MCP-driven modelling:
    - subdivide only the curved surfaces (quarter pipes, bowls, pipes, rails), detected by small
      dihedral angles between neighbouring faces;
    - crease and slightly bevel the hard edges; weighted normals;
    - displacement or normal maps for surface detail (brick, gravel).
  - **Materials:** map each original texture to a tileable CC0 PBR material (ambientCG, Poly Haven)
    tinted to the original palette; AI-upscaled originals for unique art (signs, graffiti, logos).
    Drop the baked vertex lighting when relighting, but keep it as an optional AO/dirt mask.
  - **Targets:** our SDL3 renderer with simple PBR as the portable baseline (Android, older Macs),
    and/or Unreal Engine 5 with Lumen (real-time GI, no lightmap baking) and Nanite (cheap
    high-poly/displacement), linking the C game logic as a library with UE as the renderer only.
    Lumen and Nanite need DX12/Vulkan-class desktop GPUs.
  - **First step:** after the asset loaders exist, export one level and judge the script plus a
    handful of PBR materials in Blender before building the full pipeline.
  - **Legal:** converted levels derive from the user's install and can't be redistributed (CC0
    materials can).
- Dev: 64-bit build, ASan/UBSan builds.
- Not planned by us, PRs welcome if the repo goes public: online multiplayer (rollback is feasible:
  deterministic sim, input-based replays), speedrun timer/practice mode.

## Open

- **game.c big functions (0x40aa50 etc.): coverage unverified.** The Opus agent was cut off by the
  usage limit after porting all 7 and passing their cases, before reporting instruction coverage of
  the original. Measure coverage and strengthen fixtures where needed.

- **x87 transcendentals in the native build.** `compat/x87.h` uses real x87 instructions in the hook
  build (FSIN/FPATAN for the trig lookup tables; x87 NaN propagation in the rotate helpers). The native
  fallback uses libm. Before the platform flip, generate the tables natively and compare every entry
  against the emulator's (`zmathInitTables`). If any differ, use correctly rounded values (they're
  constants; ship them as generated data computed from the original's formula).


- **Fixture bugs (not port bugs).** `saveFileRead` and `zassetRead_made` fixed 2026-10-26. Still open:
  with `BMX_GAME_DIR` set and full iterations, 18 `ziff*` cases were seen faulting inside the original at
  iter 153 (not reproduced in the 2026-10-26 full runs; recheck).
- **Signalling NaNs through x87 load/store.** The original copies some float words with FLD/FSTP
  (FT4/GT4 u/v in ngifpsx.c), which quietens an sNaN on real hardware. Unicorn keeps the bits, so the
  port copies bits to match the emulator. Decide which to follow (real hardware is the truth; the
  game probably never feeds sNaNs) before the platform flip.
- **Left out of slices:** WinMain 0x48a460
  (app entry, misfiled in zrwzgl.c, can't return in the harness); world/particle callbacks
  0x497200–0x497780 and 0x4975b0 sit in zrwtxr.c with `TODO(file)`, belong in zrwworld.c.
- More misfiled functions (left with `TODO(file)`): roller shadow 0x49b3d0/0x49b4e0/0x49b520 (in
  zrwmodelcreate.c, belongs in ngifzroller.c); asset decompressors 0x49bd10/0x49c080 (zasset);
  0x49c570 zobjDispatchEvents (zobj). zrwzgl.h and zrwmodel.h name 0x697720/0x697724 the other way
  round (gZrwScale/gZrwInvScale) and can't be included together: settle which is which.
- **What's left (97.1%, 2026-10-26):** zrwprim/zrwmodelrender/zrwcol/zrwtxr/zprofile big functions, plus the ngifzbsp/ngifzcollide slice in progress. Earlier note (86.4%, 2026-10-24): every function still `orig` in data/functions.csv except
  WinMain (0x48a460) and the zdebugFail abort trap (0x47ed10): ~40 functions of 1 KB or more,
  mostly x87-heavy (camera, rider, overlay/zoverii, ngifpsx, ngifzcollide, prop, sound, zrwprim/col).
  All Opus work, a few at a time.
- `zquatNormalize` doesn't assert on a NaN length like the original (x87 FCOM unordered).
